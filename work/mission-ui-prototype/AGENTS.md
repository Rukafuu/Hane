# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

The approved Hane workspace direction is the Figma Make file `38Ec7AheHrZceisZcyp1qy`: a light, three-column desktop messenger for collaborative agents. Reuse the official brand assets from `A:\Hane\src`; keep pink as the brand/action accent, and use distinct blue, green, amber, and red tokens for operational states. Preserve explicit human review before consequential agent actions.

Readability takes priority over the source mockup's micro-density. At normal Windows scaling, keep persistent UI text at 9px or larger, body copy at 12px or larger, and use genuine weight contrast for small labels. The workspace base should be a darker fog-gray with visibly lighter elevated surfaces; avoid a continuous near-white canvas that flattens column and card hierarchy.

2026-10-09 design decision: for the active Hane desktop messenger, the user explicitly chose the clean, minimal reading experience of the supplied Grokbot and OpenAI Dots references. This supersedes the fog-gray-shell preference for this surface: use white/near-white planes, thin neutral dividers, restrained shadows, and a clearly separated dark work preview. Keep Hane Sans, the Hane pink action accent, the three-column mission flow, and explicit human approval boundaries. Treat the references as inspiration only; do not copy their brands, mascots, content, or product chrome.

Use `Hane Sans` as the primary interface family, with `Segoe UI Variable Text`, `Segoe UI` and `system-ui` as fallbacks only. The 0.2 cut is a display cut: its 12-24 unit hairlines render as a 0,15-0,30 px gray thread at 9-15 px, and Segoe replaced it in the 2026-10-09 readability review. The WOFF2 set in `src/fonts/` is the 0.4 robust text cut (stems 88/102/116, hairlines 52/64/76 units, SemiBold 600 included, generated in `A:\Hane\src\Hane fonts\Hane-v0.4`); it reaches Segoe UI's ink at 12,5 px and beats it on solid share, and its eight hand-drawn letters (`h n a e m r l i`) are levelled to the nib-generated stems — check that with `stroke_balance` in `Hane-v0.4/sources/validate_hane.py`, which reports `stem_ratio` (drawn vs generated median width, target 1,00) and `drawn_within` (narrowest vs widest wall inside one letter, 0,86-0,90 after the fix, 0,54 before). Below 10 px prefer Medium: Regular drops under Segoe's coverage there. Keep `font-synthesis: none` so real weights, not fake bolds, carry the hierarchy. Chrome's font matching resolves 450 up to 500 and 650 down to 600, so 450 body declarations render in Medium and 650 titles in SemiBold; 400 stays for text at 12 px or more, 500 for metadata, 600 for titles and actions. Preserve comfortable line height and tabular numerals for timestamps and progress data. Small secondary text also has to clear 4,5:1 on the fog-gray shell — `--muted` and the light grays used on 9-10 px labels were darkened for that reason.

2026-10-09 product decision: with no persisted missions, show only the local onboarding agent `Hane`; do not display Orion, Byte, or Cipher until the user creates the first real mission. Hane must explain provider setup, first mission execution, and the human-review workflow without fabricating AI calls or persisting tutorial data.

2026-10-09 product decision: first-run onboarding asks for explicit, optional local-folder read permission and GitHub device authorization before the first mission. A selected local folder remains browser-local and does not grant agents new capabilities; GitHub tokens remain only in Windows Credential Manager while SQLite stores the account label, scopes, and connection time. Both steps are skippable and GitHub stays unavailable until Hane is started with a GitHub OAuth App Client ID.

2026-10-09 product decision: onboarding is a five-message conversation, revealing one choice at a time. It never assumes permission: provider, local folder, and GitHub can each be skipped. The final message creates locally persisted visual Hane profiles (name, color, shape, optional image/GIF); they do not silently change the planner/executor/reviewer runtime contract.

2026-10-09 design decision: the sequential onboarding reads as a calm conversation, not a checklist or settings card. Center the current Hane message, show a compact progress cue, place the prompt in one soft chat bubble, and reserve the pink filled button for the single primary choice; secondary and permission-opening actions remain quiet text actions.

2026-10-09 design decision: the mission context panel (right column) must be collapsible like a sidebar (user reference: Dribbble sidebar-animation patterns). The column narrows while the content slides out, an edge tab on the conversation's right border takes over the reopen toggle, `Ctrl/Cmd + \` toggles, and the state persists in `localStorage` under `hane-panel-open`. The collapse transition is CSS on `grid-template-columns` (layout, not a motion.js-owned property) and is disabled under `prefers-reduced-motion`.

2026-10-10 product decision: the real global Settings sheet must be independently scrollable (it replaces the app shell, so it needs a viewport-bounded scrolling region). It includes persisted local Appearance preferences: Midnight, Forest, and Paper color modes; a user accent color; System/Hane Sans/monospace font choice; and Compact/Comfortable/Large text scale. Default to Midnight with a restrained blue accent for low-glare reading, while retaining Paper as an opt-in light mode. Apply preferences to both the Settings sheet and mission workspace; do not implement them only in an unrelated visual sandbox.

2026-10-10 visual decision: selecting a theme applies its paired accent instead of carrying a stale color from the prior theme: Midnight uses blue, Forest uses green, and the light option is named `Hane claro` and restores Hane's base pink `#ed799a`. The font control calls the optional cut `Hane Sans (beta)`.

2026-10-10 usability decision: preserve the three-column desktop at normal width, but below 980px or at high Windows zoom collapse the left navigation into an accessible icon rail and expose mission context as an explicit drawer. The drawer starts closed in compact view so it cannot cover the composer; its trigger, Escape, and Ctrl/Cmd+\\ must remain keyboard-accessible. Midnight and Forest must never pair light text with light cards: onboarding, composer popovers, empty states, and contextual controls use the dark theme tokens.

2026-10-10 accessibility decision: the Compact, Confortável, and Grande choices are whole-product reading preferences. They must reach sidebar navigation, mission headers and output, onboarding, composer, contextual drawer, audit evidence, and approval controls; no choice may silently leave the primary workflow at an unrelated fixed size.

2026-10-10 appearance decision: the accent control exposes its hex value, accessible quick swatches, and a reset to the selected theme's paired color. Resetting an accent must not overwrite the user’s selected font or text scale; the broader “Restaurar padrão” remains the only full-preference reset.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

Motion uses anime.js v4 (`animate`, `stagger`) and lives only in `src/motion.js`; components import helpers from there instead of calling anime.js directly. Keep animation values explicit (`[from, to]`) because anime.js seeds its transform model from inline styles, not class rules, and every mount animation must `revert()` on cleanup so React StrictMode replays correctly. CSS must not animate properties owned by motion (the spinner, toast entry, and leader toggle knob are driven by anime.js). Honor `prefers-reduced-motion` through the shared `reduceMotion()` guard.


2026-10-10 product decision: replace the first-run conversation with three dedicated stages: personal local profile, optional provider, optional first group. One personal profile per SQLite installation, distinct from visual agent profiles. Backend sessions, optional Argon2id protection and processed local photos are real; no profile secrets in browser storage. The sidebar footer offers Meu perfil, Configurações, Bloquear Hane and Sobre. Blocking protects the UI/API, not files at rest; independent multiple profiles remain deferred. Existing provider, folder and GitHub settings stay available and never gain permissions automatically.

2026-10-10 product decision: local password recovery uses an offline single-use recovery code, independent of Windows or other OS authentication. Show once with explicit save/print and acknowledgement, store only its verifier, regenerate only with current-password reauthentication, rotate on password changes/recovery, and revoke all sessions after recovery. Losing both password and recovery code has no in-app recovery. Existing password profiles must generate their first code while authenticated; never invent a recovery path during migration.

2026-10-10 product decision: Hane Garden belongs on a dedicated welcome screen BEFORE personal profile creation, not in the three-stage onboarding form. Show it only when no local personal profile exists; the explicit “Começar meu Hane” action enters the existing creation flow. Returning profiles keep their existing workspace/unlock path. Keep Garden interaction entirely visual, local, optional and independent of profile persistence.

2026-10-10 follow-up: the user also requested Hane Garden on the “Comece sendo você” profile screen shown in their screenshot. Reuse it across the three onboarding stages while keeping the separate welcome screen. Personal photos accept GIF with preserved animation, validated and re-encoded to local WebP; enforce upload, aggregate pixel and frame limits.


2026-10-10 agent architecture decision: Hane is the only agent automatically created at onboarding, with a persistent ID. User-created agents separate Identity, Behavior, and Capabilities in settings. Individual conversations talk directly to the selected agent without requiring an execution team. There is no special execution rule for greetings. In a group, a message without an explicit agent recipient is addressed to all participants: every participant responds using their own identity and instructions, and they coordinate the message among themselves. Explicitly addressed messages select the named agent as recipient. Planning and review are optional internal stages, not automatic agent identities. Groups contain at most eight existing agents; enforce the limit in both UI and backend for creation and changes. Leadership is explicit and optional; dynamic coordination stays bounded and auditable. The backend validates permissions per operation independently of prompt text or imported instructions. See docs/decisions.md ADR-0009; do not present the currently fixed ROLE_FLOW as already replaced.
